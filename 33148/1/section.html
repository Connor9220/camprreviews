PR #33148 - CAM: Fix full-circle detection in PathSegmentWalker (Rimas2200)

TL;DR

  • Fix works: the arc from issue #32741 now draws as a full circle after recompute, and full-circle G2/G3 moves no longer randomly vanish (133 of 500 random exact full circles collapsed on main, 0 on the PR).
  • One small regression (edge case, nit): a "full circle" whose end point sits on the same radial line as the start but a hair off in radius (e.g. G0 X25 Y0 / G2 X25.001 Y0 I-5 J0, typical of rounded imported G-code) was drawn as a full circle on main and now draws nothing.
  • New gtest (143 CAM C++ tests) passes; full TestCAMApp suite passes (1990 tests, OK).

What the PR changes

PathSegmentWalker::walk() arc branch: full circles are now recognized by exact equality of the projected start/end points (any GetAngle() result that is finite becomes 2 pi). The G2/G3 "use the major angle" flip is rewritten as anorm.z * norm.z < 0, which is equivalent to the old two-branch test for every non-zero cross product. The old fallback else if (angle == 0) angle = 2 pi (cross product exactly zero and angle exactly zero) is removed. PathSegmentWalker feeds three callers: the 3D path rendering (ViewProviderPath), Toolpath.BoundBox (Path.getBoundBox), and Area::getClearedArea() (rest machining cleared area). All three change the same way.

Finding (nit)

Radially-mismatched full circle disappears. When the end point equals the start angle-wise but differs a little in radius (cross product exactly 0, GetAngle() exactly 0), main fell into else if (angle == 0) angle = 2 pi and drew a full circle; the PR drops that fallback, so the sweep is 0 and the circle is not drawn (and is left out of the BoundBox / cleared area). LinuxCNC treats such a move as a full circle (radius difference within its tolerance), so the preview hides a cut the machine makes. Real-world source: imported or hand-written G-code with rounded coordinates (circle starting at 0/90/180/270 degrees, end rounded differently from the start). Rare; CAM's own generators emit half circles (Area, helix, thread milling), so FreeCAD-generated paths are not affected. Possible fix: keep the old fallback after the new checks (else if (angle == 0 && anorm.*pz == 0) angle = 2 pi). Repro:

  1. Custom op, G-code G0 X25 Y0 Z0 then G2 X25.001 Y0 I-5 J0.
  2. Recompute: main shows the circle, PR shows only the rapid.
