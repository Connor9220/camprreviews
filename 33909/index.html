TL;DR

  • No defects found. Both fixes do what the PR says, and the full CAM test suite passes.
  • Fix 1 (arcs): on main, an Adaptive rest op that actually sees a previous op's cleared area stops with an AssertionError and has no path. On the PR it recomputes. Tested in standard mode, model-aware mode and on a tilted work plane.
  • Fix 2 (depth): on main, rest machining looks for cleared area at Z=0. For a model sitting on Z 0..20 it never finds the roughing pass, so a 3 mm rest op re-clears the whole pocket (8864 mm of feed). On the PR it cuts only the corners and the ring around the island (669 mm of feed), leaves no reachable floor uncut, and doesn't gouge.
  • Existing jobs with Use Rest Machining on will get different (correct) toolpaths when they recompute.

What the PR does

Two changes in Path/Op/Adaptive.py, plus one new unit test:

  1. get_cleared_area() accepted only straight edges in the cleared-area shape (assert edge.Curve.TypeId == "Part::GeomLine"). Since the Clipper/arc-fitting changes, Area.getClearedArea() returns arcs as well. The PR discretizes Part::GeomCircle edges instead of asserting.
  2. Execute() (standard, not model-aware) now passes obj.FinalDepth.Value as the cleared-area check height. Before, it used the Z of the working edges, which combineHorizontalFaces() flattens to Z=0. The model-aware path already passed explicit depths.

Code review findings checked and dropped

/code-review medium 33909 raised eight items. None turned out to be a defect:

  • Arc edges might be reversed or out of order in the wire. Area::toShape(CCurve) builds each arc with its axis at ±Z to match the travel direction, adds edges in travel order, and the main code already relied on Vertexes[0] for lines. On the real cleared area (59 edges, 41 of them arcs) there were 0 reversed edges and 0 gaps between consecutive edges. Checked, fine.
  • The assert would still trip on other curve types. toShape only produces lines and circles. Dropped.
  • Final Depth for every step-down re-clears upper levels when the previous op stopped short of the floor. This is conservative, not wrong: one 2D path is reused for every level, so only area cleared down to the floor is safe to skip. Seen in the half-depth case above. Not a defect.
  • Fine 0.002 mm arc deflection makes the input state larger. 335 points here. No measurable effect.
  • Code-quality items (an existing helper in adaptive_common.py, the unused zOverride=None default, the fixed document name in the test): not defects.

Also on main (not this PR)

  • The rest op's recompute spends about 31 s inside PathOpUtil.getClearedAreas() (core Path.getClearedArea) for this 14.5k-command roughing pass. main takes the same 31 s (30.8 s vs 31.8 s) whenever it actually sees the cleared area. Users will notice it more now, because on a normal Z 0..20 model main never got that far.
