What changed since the last review

The earlier head moved the input faces to Z −5 but returned the result at Z 0. Because of that, the order-restore step could not match any faces. Pocket Shape with Sorting Mode = Manual then silently fell back to X order.

The rewrite drops the extrude-and-fuse approach:

  • Every face is moved to the same height z.
  • The faces are cut from a bounding-box face with a fuzzy cut (tol = 0.01).
  • The result faces are rebuilt from cut.Wires[1:] with FaceMakerBullseye.

Inputs and outputs are now at the same height, so the order restore works again.

Profile with edges or walls only

Profile now always passes its (possibly empty) flat-face list to the combine step. With only edges or only side walls selected, both ops still generate correct paths. The empty list does log Geom.INFO: Zero working area to process. Check your selection and settings. once per recompute. That is INFO level, so it is hidden at the default CAM log level (NOTICE) and only shows with verbose logging. This is a nit only; returning early when the face list is empty would avoid it.

Issues

  • #30876 (referenced as "Fixes #30876"): fixed. Reproduced on main and on the PR with the reporter's own file; Individually now matches Collectively.

Not in the PR description

  • Profile merges touching or overlapping flat faces across heights, in both Individually and Collectively modes (tested). The description says "Combined connected horizontal faces". It does not say that faces at different Z are merged into one silhouette, or that an inner edge of one face that another selected face fills is no longer profiled.
    • Example: boss top plus the surrounding base face, processHoles on. Main cut the outer edge, a loop around the boss, and a "hole" loop inside the boss footprint. The PR cuts only the outer edge.
    • The old hole loop cut into the boss, so losing it is an improvement.
    • Anyone who relied on this to profile a boss and its base in one op now needs to select the boss side walls instead.
  • Faces less than 0.01 mm apart now merge in Profile, Pocket Shape and Adaptive, because of the fixed fuzzy tolerance (tested). A 0.005 mm gap gave 2 faces on main and 1 on the PR; 0.02 mm and 0.1 mm gaps stay separate. The tolerance is hard-coded and does not use the Job's Geometry Tolerance.
  • Pocket Z values move by about 1e-14 mm (tested). This is the reason for the TestSlicer change; it has no effect on G-code.
  • combineHorizontalFaces gains z and tol parameters (API only, not user-facing; covered by the new tests).
