TL;DR

  • Fixes #33470 for new Adaptive operations: the helical entry now runs at the tool controller's Ramp feed, and the clearing keeps the Horizontal feed.
  • Minor defect: the straight vertical move down to the start of each helix also gets the Ramp feed. Before the PR it used the Vertical feed. With the default Ramp feed (= Horizontal feed), that plunge now runs at the Horizontal feed.
  • Not in the description: existing Adaptive operations opened on the PR switch their helix from the Horizontal feed (main) to the Vertical feed. On the test block that is 180 to 59.4 in/min and adds 8 s of cycle time. They also get a new, visible "Helix Feed Version" property.

Findings

Straight move down to the helix start now uses the Ramp feed (minor)

_applyFeedRate(helixCommands, entryFeed) (src/Mod/CAM/Path/Op/Adaptive.py:282) overwrites F on every G1/G2/G3 of the helix block. That includes helixCommands[2], the straight G1 Z<pass start> from Safe Height down to the top of the helix. Before the PR, PathFeedRate.setFeedRate classified that move as vertical and gave it VertFeed. On new ops it now gets RampFeed. A new tool controller's RampFeed is the expression HorizFeed, so by default the vertical plunge runs at the horizontal feed.

New op, pocket-island job, HorizFeed 1000 / VertFeed 100 / RampFeed 300 mm/min:

first helix-block move G1 Z23.175 PR base PR
feed 100 mm/min (VertFeed) 300 mm/min (RampFeed)
helix arcs 1000 mm/min (HorizFeed) 300 mm/min (RampFeed)
clearing 1000 1000
op cycle time 10:07 10:26

On the twp block after opting in (version 1, RampFeed 30 in/min) the same move runs at 30 in/min, against 59.4 (VertFeed) on main. The move usually ends at stock top or inside the bore cut by the previous pass, so it is mostly in air. It is still a straight Z feed that ignores the Vertical feed, and the PR only meant to change the helix. Skipping the first mill move (or only overwriting moves that change XY) would keep VertFeed there.

Repro:

  1. Create a new Adaptive op with a tool controller where Ramp feed differs from Vertical feed.
  2. Recompute and look at the first G1 after (Helix to depth: ...): it is a Z-only move at the Ramp feed.

From the code (not reproduced)

  • src/Mod/CAM/CAMTests/TestPathAdaptive.py:1329-1335: after adaptive.HelixFeedVersion = 1 the test reads helixFeeds, _ = ... and then asserts on adaptiveFeeds left over from the version 0 run. The last two assertions never check the clearing feeds after opting in.
  • src/Mod/CAM/Path/Op/Adaptive.py:166-172: HelixFeedVersion is a free integer whose tooltip is not wrapped in QT_TRANSLATE_NOOP like the other Adaptive properties. Any non-zero value (2, -1) means "use RampFeed". A boolean or a two-item enumeration would be clearer for the users who see it on old ops.

Dropped: an early recompute() in Base.onDocumentRestored before opOnDocumentRestored adds the property. It only applies to very old files with a LinkSubList Base, and the same applies to HelixConeAngle on main. Also dropped: the redundant setFeedRate pass and the over-broad migration tests, which are cleanups, not defects.

Not in the PR description

The description says the Ramp feed tooltip "is now the only user visible change in the UI". The diff also brings:

  • Old Adaptive ops change their helix feed (tested). Any Adaptive op saved without HelixFeedVersion (all files from main / 26.3rc) is migrated to version 0, which uses VertFeed for the whole helix block. On main since #22357 the helix arcs use HorizFeed. On twp-test-block-job.FCStd (HorizFeed 180, VertFeed 59.4 in/min):

    op main helix feeds PR helix feeds cycle time main / PR
    Adaptive Top Pocket 59.4 (straight move) + 180 (arcs) 59.4 2:12 / 2:20
    Adaptive Facet30 Pocket 59.4 + 180 59.4 0:21 / 0:24

    Clearing feeds are unchanged (180). This matches what reviewers asked for in the thread (restore the 1.1 behavior). But the code comment "Operations saved without a version retain their legacy entry feed" is only true against 1.1, not against main or 26.3rc files, and users opening those files get a slower helix without notice.

  • New property Helix Feed Version (group "Adaptive Helix Entry") (tested). It is visible and editable on migrated ops (0) and hidden on new ops (1). Setting it to 1 on an old op switches the helix to RampFeed. Checked in the Property View and on a scripted new op (HelixFeedVersion = 1, editor mode Hidden).

  • The flat finish circle at the bottom of the helix and the straight move down to it use the entry feed (tested). See the finding above.

  • The connecting spiral used with Helix Cone Angle > 0 also uses the entry feed (not tested in FreeCAD). Only the new unit test covers it.

Issues

  • #33470 (Adaptive: no separate feed for the helical plunge): fixed for new ops. On the base, a new op's helix used VertFeed and HorizFeed (100 / 1000 mm/min) with no separate control. On the PR it follows RampFeed (300) while the clearing stays at 1000. Old ops need Helix Feed Version set to 1 first (shown in the video).

Unit tests
