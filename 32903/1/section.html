PR #32903 — CAM: Operations respect workplane frame

TL;DR

  • One dressup was left behind by the move to plane coordinates: Path Boundary now rapids inside the part, 12–14 mm below the top of a 20 mm block.
  • Rest machining reads a previous operation's cleared area in the wrong place when two operations share a tool axis but not a plane origin — measured 30 mm out. The correction that was meant to fix this never runs.
  • An operation's Placement is now read-only and rewritten on every recompute. A document that positioned an operation with its Placement loses that offset silently the first time it recomputes.
  • ~~A plain three-axis Profile changes where it plunges.~~ Withdrawn — see "Test block and trays" below. The plunge point flips between two seams from one recompute to the next on main as well, so it is pre-existing Profile nondeterminism, not this PR.
  • The September 24 test suite was re-run on this head: the multi-face TWP block and both class trays recompute clean, all eleven bugs from that report are still fixed, and nothing regressed. No new defect.

Everything the PR description claims does work: a work plane's origin is really consumed now, depths on a datum plane read from the plane, the rotary gating moved from generation to the post, and the plane's Fixture is emitted. The findings below are gaps around the edges of that change.

Findings

1. The Path Boundary dressup was not moved into the operation's frame — it rapids inside the part

Path/Dressup/Gui/Boundary2.py (the CAM_DressupPathBoundary2 command) is the one dressup that did not get PathDressup.placeWithBase(). It still does

wires = Path.Geom.wiresForPath(PathUtils.getPathWithPlacement(obj.Base))
...
clearanceHeight = baseOp.ClearanceHeight.Value
safeHeight = baseOp.SafeHeight.Value

so it mixes two frames in one path: the cut moves come from the base operation's placed path (world coordinates, correct), while the linking moves are built from the base operation's Clearance and Safe heights, which after this PR are measured from the work plane.

Measured on datum_boundary.FCStd (a 100 × 100 × 20 block, work plane on the top face at Z 20, 5 mm endmill):

Profile (base op) Path Boundary dressup
Placement (50, 50, 20) identity
stored Z 0 / 6.175 / 8.175 (plane frame) 6.175 / 8.175 / 20.0 (mixed)

The dressup's whole G-code:

G0 Z8.175000              ; "clearance" - 11.8 mm below the top of the part
G0 X60.000000 Y-2.500000
G0 Z6.175000              ; "safe height" - 13.8 mm below the top of the part
G1 X0.000000 Y-2.500000 Z20.000001   ; feeds UP to the cut
G2 I0.000000 J2.500000 X-2.500000 Y0.000000 Z20.000001
G1 X-2.500000 Y100.000000 Z20.000001
G2 I2.500000 J0.000000 X0.000000 Y102.500000 Z20.000001
G1 X60.000000 Y102.500000 Z20.000001
G0 Z8.175000              ; retracts INTO the part

Two rapids straight through solid material and a feed move used as an approach. See boundary_dressup_iso.png, boundary_dressup_heights.png and the video.

Second consequence: because the dressup's own Placement stays identity, the post's _expand_workplane_frames() reads item.source.Placement, finds identity, and treats the dressup as an operation with no work plane. A tilted operation wrapped in this dressup is therefore neither refused nor rotated nor declared by a current post — its world-coordinate 3D path goes out as if it were a three-axis program. (The legacy-post guard is safe here: _refuse_tilted_operations() looks through PathDressup.baseOp(op).)

Under cam_ab the PR side also logged, on recompute:

Path/Dressup/Gui/Boundary2.py", line 187, in execute
    linkingMoves = linking.get_linking_moves(**linkingArgs)
RuntimeError: No collision-free path found between start and target positions

which is the linking generator noticing the inconsistency.

2. getClearedAreas() returns the cleared area in the wrong frame — the correction is dead code

Path/Op/Util.py:

cleared = op.Path.getClearedArea(diameter, localBox.ZMin + tol + dz, localBox)
if back is not None and cleared is not None and hasattr(cleared, "transformShape"):
    cleared.transformShape(back, False, False)

Path.Path.getClearedArea() returns a Path.Area, which has no transformShape:

>>> ca = p.getClearedArea(5.0, -0.9, bb)
>>> type(ca), hasattr(ca, "transformShape")
(<class 'Path.Area'>, False)

so the hasattr guard silently swallows the back-transform every time. The bounding box is carried into the other operation's frame, the area is computed there — and then handed back in that frame instead of the caller's. The docstring ("the cleared area computed there, and the result carried back") and sameWorkplane()'s new docstring ("the one thing that has to move … which getClearedAreas() shifts by the plane origin") both describe behaviour that does not happen.

Measured: a first operation cutting a 40 × 20 rectangle on a Z-up datum plane whose origin is at (30, 10, 0); a second operation with no plane; identical tool.

cleared area handed to op 2 : X -2.53 .. 42.53   Y -2.53 .. 22.53
region actually cleared     : X 27.47 .. 72.53   Y  7.47 .. 32.53

30 mm out in X and 10 mm in Y — exactly the plane origin. Callers are Path/Op/Area.py (Pocket & friends, UseRestMachining) and Path/Op/Adaptive.py. The effect is that a rest-machining operation skips material that is still there and re-cuts air somewhere else. Before this PR a Z-up plane's origin was not consumed at all, so this could not happen.

See cleared_area_offset.png.

Note also that getClearedArea()'s return type means the whole back/localBox machinery needs a different mechanism (transform the resulting TopoShape, or transform the path instead) rather than a guard.

3. An operation's Placement is now read-only and is rewritten on every recompute

Path/Op/Base.py now ends execute() with

frame = PathUtil.workplaneForOp(obj)
if not obj.Placement.isSame(frame, 1e-9):
    obj.Placement = frame

and lists Placement in setEditorModes() as read-only. For an operation with no work plane, frame is the identity, so any Placement the user had set is discarded:

op.Placement = FreeCAD.Placement(FreeCAD.Vector(25, 0, 0), FreeCAD.Rotation())
op.touch(); doc.recompute()
op.Placement.Base     # -> Vector (0.0, 0.0, 0.0)
op.getEditorMode("Placement")   # -> ['ReadOnly']

Before this PR nothing wrote obj.Placement (there was an explicit comment saying nothing should), the property was editable, and PathUtils.getPathWithPlacement() honoured it throughout — the legacy posts, Inspect and the simulators all read operations through it. So an existing document in which somebody offset an operation by its Placement loses that offset at the first recompute, silently and without an undo-able user action.

This is clearly deliberate (the Placement is the frame now), but it is a capability removed from saved files and it is not in the PR description. Worth either a migration that turns a non-identity Placement into a work plane (_adoptFrameAsWorkplane() already exists for the older vector form) or a note in the release notes.

4. A plain three-axis Profile changes where it plunges — WITHDRAWN

Withdrawn. Re-testing against main (see "Test block and trays") showed the same Profile flipping between the two seams from one recompute to the next, on main and on the PR alike. The A/B below caught that instability, not a change made by this PR. The rest of this section is kept for the record; the reproducibility bug it actually found is described in the new section.

Same wire, same direction, same length — the seam has rotated by one vertex, so the tool now plunges at the corner-arc end (−2.5, 0) instead of mid-edge (0, −2.5), and the leading corner arc becomes the closing one. Tag positions are unchanged; only the listing order and the entry point move.

I could not pin this to a single commit within the PR (UseStartPoint is False in this job, so the Area.py self.startPoint(obj) change is not the cause), but it is inside the PR: the A/B is against the PR's own base and is deterministic (base-vs-base returns IDENTICAL).

It is not a wrong toolpath, but it means "a three-axis job is byte-identical to before" — which the new code comments assert in several places — does not hold for closed profiles, and every existing Profile's plunge point moves.

(The claim in the last sentence of the previous paragraph is what the re-test disproved: "base-vs-base returns IDENTICAL" was one sample of a coin flip. See the new section.)

Rapids and gouges

cam_gouge_check reads an operation's stored path and does not apply its Placement, so on a work-plane job it compares plane-frame coordinates against world solids. On tray B it reports "8 cuts" for DressupLeadInOut — the same world moves tray A passes cleanly — so its verdicts were only used where every Placement is identity. On tray A it is clean: Adaptive (rapids and links, 332 moves), DressupLeadInOut (12 rapids, 3 links, 45 cuts / 753 segments) and DressupLeadInOut001 all report no gouges. On the TWP block it did not return inside the client timeout.

Instead, every rapid of every non-Adaptive op in the block was swept against the job's model solids in world coordinates. No rapid has both ends inside the part. The only moves that pass through material are the combined X/Y/Z linking rapids that climb from cut depth to safe height — the ordinary FreeCAD linking form, unchanged by this PR.

Correction: the three-axis Profile plunge point (finding 4)

plain3axis.FCStd A/B'd against main with cam_ab reproduced a Profile difference — but with the sides the other way round from the original run against the PR's base. Chasing that:

  • main vs HEAD, run twice with the same probe: first run main = 227b15c0, HEAD = 925b9dd3; second run both 227b15c0.
  • A probe that touches and recomputes the same Profile 12 times in one process:
    • main: 227b 227b 925b 227b 925b 925b 925b 925b 925b 925b 227b 925b
    • PR: 227b 925b 925b 227b 925b 925b 227b 925b 227b 925b 227b 925b
  • In the GUI instance, six recomputes of an untouched Profile gave 925b five times then 227b.

The two values are the two seams: plunge at (0, −2.5) with the corner arc leading, or at (−2.5, 0) with it closing. Same wire, same direction, same length. Both appear on main and on the PR, at random, without any input changing.

So finding 4 is withdrawn as a PR defect. What it actually found is a pre-existing reproducibility bug: a closed Profile's entry point is not stable from one recompute to the next, which means no Profile job is byte-reproducible and any A/B on a closed Profile needs repeating before it is believed. Worth its own issue against main, not this PR. profile_seam_flip.png shows the two runs overlaid: one wire, two plunge lines.
