How the base commit was measured

The base commit's C++ is the same as main's. Its getClearedArea turns every line and arc at or below the depth into a 2-vertex curve, then makes one CArea::Thicken(radius) call that unions them all. That libarea function is not changed by this PR and can be called from Python through the area module. So I re-created the old visitor in Python (G0/G1/G2/G3, absolute, G17, which is all the test file has), applied the same accuracy and clipper settings, and timed the Thicken call on the same paths the macro uses. The geometry was then compared with the PR's result.

  • "Base" below is only the Thicken time: the old union, which is where the old code spent its time.
  • "PR union" is the PR's getClearedArea time minus path walking and the OCC shape conversion, read from its debug timing output. This matches the base number most closely.
  • "PR call" is the whole Path.getClearedArea() call from Python. The macro measures the same thing.
  • PR numbers are the median of 3 runs. Base numbers are the median of 3 runs, except the four Adaptive cases, which were run once (each takes seconds).

Segment counts are the base visitor's. The PR skips zero-length moves (vertical plunges), so it counts a few fewer (for example 3155 vs 3308 for Adaptive005). Base times under about 10 ms are noisy: one Python-side run of ZigZag70 took 26 ms, the others 7 ms.

Where the PR is slower (not a defect, for tuning)

  • Circle union in pockets. For ZigZag, Line and Grid pockets the circle filter keeps almost every end cap (for example PocketRestGrid30: 404 centers, 404 circles), because every pass ends at a wall. The circle union is then the biggest stage (31 of 62 ms on Grid30, 54 of 108 ms on Big ZigZag30).
  • Open-path difference on 70% stepover big pockets. On BigPocketRestZigZag70 and ZigZagOffset70 the open difference of the deferred center lines takes about 90 ms of the 140 ms, while the old union took 58 ms and 27 ms.
  • Adaptive paths (thousands of short segments) are where the old code was slow, and there the PR is 100x to 700x faster.

Geometry: is the new cleared area the same?

For each of the 25 cases I built OCC faces from the base result and from the PR result and cut each from the other:

  • Adaptive (4): PR-only area 0.004 to 0.006 mm², base-only area at most 0.0013 mm², in pieces under 0.001 mm wide.
  • Small pockets (15): Offset and Helix match exactly. ZigZag, Line and Grid differ by at most 0.13 mm² in total, in slivers under 0.001 mm wide. Offset70 and Helix70 have one 0.0011 mm² base-only piece, about 0.02 mm wide.
  • Big pockets (6): ZigZagOffset matches exactly. ZigZag: the PR area is 0.3 to 0.5 mm² smaller, in 178 to 317 slivers, each under 0.001 mm wide.
  • Nowhere does the PR claim a cleared region wider than 0.001 mm that the old code did not. That's well inside the 0.03 mm buffer getClearedArea adds, so rest machining will not skip material because of this change.

Not in the PR description

  • Full-circle arcs are now counted as cleared (tested, fix). On main, a G2/G3 whose start equals its end adds nothing to the cleared area, so rest machining after a Helix or helix-entry pass that makes full circles at depth re-cuts what they cleared. The PR splits them into two half circles.
  • The region of interest is now really enlarged by the tool radius (tested, fix). On main the constructor's bbox.Enlarge(radius) enlarged its parameter, not the member, so a pass within one tool radius outside the region was ignored. The PR fixes this with this->bbox, and my zigzag test shows that pass now counted at the region edge.
  • Arcs outside the region are now skipped, and zero-length moves too (tested indirectly: results match the base inside the region).
  • New MinArcPoints property on every Path Area object (Path::FeatureArea, libarea group, integer, default 4, "Minimum segments for arc discretization"), also a new Path.Area parameter (tested: it shows on a new object with default 4. Not tested: loading an old file that has an Area object, which should just get the default).
  • Debug output (tested): every getClearedArea call prints a getClearedArea: total=... line to stderr, and setting CLEARED_AREA_DUMP_DIR writes JSON dumps. The last commit's title says so. It should come out before merge.

Included from #33909

  • Arcs in the input cleared area (tested, fixed). A/B, main's Adaptive.py vs the PR's on the author's file: Adaptive005 and Adaptive007 end up Invalid with 1 command on main. On the PR they compute (1783 and 1430 commands, minimum Z -5).
  • Depth used when checking previous paths (tested, fixed). Model-aware Adaptive014 and Adaptive015 ignore the roughing op's cleared area on main and re-cut the whole pocket (58,736 and 46,674 commands, about 8100 mm of feed). On the PR they cut only the rest (1005 and 1182 commands, about 205 mm).
  • New test testRestMachining (tested): passes.
