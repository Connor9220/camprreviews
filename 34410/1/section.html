PR #34410: CAM: fix operations getting marked as dirty after getClearedArea is called

TL;DR

  • No defects found. The fix works: after the PR, a rest-machining operation no longer leaves the earlier operations it reads marked as needing a recompute.
  • Before the PR, reading an earlier op's path for rest machining wrote that path back onto the op, which marked it dirty. I confirmed this from the code, not by running it: no pre-PR build was available in this job.
  • Toolpaths don't change. The full CAM unit test suite passes.

Requester's question

validate that before this pr when a rest machining op computes, the operations it takes into account get marked dirty, and that after this pr they do not

After the PR (tested at runtime): they are not marked dirty. I tested this on a two-pocket job in the review tree's FreeCAD (PR build):

  1. A 120x70x20 block with a 40x40x8 pocket around a round island (Ø12).
  2. RoughPocket: Pocket Shape, 10 mm end mill, Final Depth 12, Step Down 4, Extra Offset 3 mm. It leaves a 3 mm wall of stock (feed extent X 18-42, Y 23-47).
  3. RestPocket: a copy of RoughPocket made with CAM_OperationCopy in the same Job, with Use Rest Machining = true and Extra Offset 0. It cuts only the 3 mm ring left on the walls and around the island (feed extent X 15-45, Y 20-50; 631.7 mm of feed against 326.3 mm for the rough pass). So getClearedAreas() really does read RoughPocket's path through Path.getClearedArea().
  4. I changed only RestPocket (Comment, then Step Down 4 → 3 → 4 mm through the Property View in the demo) and recomputed. RestPocket recomputed each time (its new comment shows up in its path), and RoughPocket stayed Up-to-date afterwards. So did the other ops. Nothing was left touched, and the Report view stayed free of errors.

Before the PR: they are marked dirty. I confirmed this from the code, but couldn't reproduce it at runtime here. The chain on main:

  • Path/Op/Util.py:591 does path = op.Path. PyObjectBase::__getattro (src/Base/PyObjectBase.cpp:326-331, ATTR_TRACKING is defined) tags the returned Path.Toolpath object with its parent (the op) and the attribute name Path.
  • Util.py:599 then calls path.getClearedArea(...). For a method that isn't marked @constmethod, the binding generator (src/Tools/bindings/templates/templateClassPyExport.py:692-694) emits startNotify() after the call. You can see it in this build's generated PathPy.cpp: setFromGCode still has it, and getClearedArea no longer does.
  • PyObjectBase::startNotify() (PyObjectBase.cpp:505-535) calls __setattro(parent, "Path", this), which means op.Path = path. That sets the op's Path property and touches the op, mid-recompute of the rest op.
  • So on main, every earlier op that the rest op considers, in the same work plane frame, is left touched after the rest op computes. If the earlier op is a dressup (and not a rest-machining pass), the dressup is touched. Ops on a parallel work plane at a different origin go through PathUtil.applyPlacementToPath() first. That returns a fresh, untracked path, so on main those ops were not touched either.

Why not reproduced: this is a C++ binding change, so the "before" side needs a FreeCAD binary built from main. cam_ab only swaps CAM Python. This job has only the PR build, and it may not rebuild or edit the review tree. The bridge's execute_python was declined (code approval), so I didn't run scripted probes such as calling a still non-const Path method on op.Path to show the same notify path. All runtime checks used the bridge's structured tools (cam_fixture, gui_run_command, edit_object, recompute_document, cam_path_stats) and the recorded demo.

What I checked

  • Diff: two lines. @constmethod on getClearedArea in App/Path.pyi, and PathPy::getClearedArea(...) const in App/PathPyImp.cpp. The body only reads getToolpathPtr() (a const accessor) and passes it to Area::getClearedArea(const Toolpath*, ...), so the method really is const.
  • Generated binding (PR build): staticCallback_getClearedArea no longer has the isConst() rejection or the startNotify() call. The truly mutating methods (addCommands, insertCommand, deleteCommand, setFromGCode) keep both. toGCode, copy and getCycleTime were already const.
  • Callers: the only Python caller is Path/Op/Util.py:getClearedAreas(), used by rest machining in Path/Op/Area.py:305 (Pocket and other Area ops) and Path/Op/Adaptive.py:518. Nothing relied on the old write-back.
  • Toolpaths: unchanged by design. The method's result is the same; only the side effect on the owning op goes away. I didn't run a main-vs-PR toolpath A/B, because the change is in the binding layer and cam_ab can't swap it.
  • Unit tests: the full CAM suite (TestCAMApp) ran 2137 tests: OK (11 skipped, 4 expected failures). The PR adds no test. A test in TestPathOpUtil could recompute, call getClearedAreas() and assert that the earlier op isn't Touched.
  • Code review (/code-review medium 34410): no correctness findings. It raised two notes, which I dropped: the missing regression test (not a defect), and Command.transform also not being marked const (also on main, not part of this PR).
