Reproduced: Yes

TL;DR

  • The test is TestPathAdaptive.testRestMachining. Run alone it aborts with the reporter's assertion, std::list<heeks::CVertex>::front(), '!this->empty()'.
  • The bug is in CArea::NaiveOffset, not the test. A path move with no XY travel gives a curve of only zero-length segments. The offset curve stays empty, and front() is called on it.
  • Normal builds don't crash. Reading the empty list happens to do no harm, and that move just adds nothing to the cleared area.
  • Fix tested: with the patch, all 2097 CAM tests pass with assertions on, headless and in the GUI. Adaptive toolpaths are byte-identical on two models.

How it was reproduced

The tree was a clean build of upstream main 5ce3b8804dd, which includes the Adaptive move to Clipper2 (#33739). The reporter's commit b9fb94ca48a has the same AreaClipper.cpp and Area.cpp.

The flag alone does not reproduce it here. The pixi environment uses libstdc++ 13.4, whose std::list::front() has no empty check, so a build with -D_GLIBCXX_ASSERTIONS passes every test. The reporter's libstdc++ 16 has that check.

To match it, GCC 16-style checks were added to a copy of bits/stl_list.h (front, back, pop_front, pop_back). libarea-native, area and PathApp were then rebuilt against that copy with -D_GLIBCXX_ASSERTIONS.

This was x86_64 with clang, not the reporter's Fedora aarch64 GCC 16 build. Only those three libraries had assertions on.

Why it happens

get_cleared_area in Path/Op/Adaptive.py calls Path.getClearedArea on the earlier ops when UseRestMachining is on. ClearedAreaSegmentVisitor::line() makes a 2-vertex curve for every G0/G1 at or below the depth, then Thicken offsets them all.

The roughing path in this test has 46 moves that end where they start, for example a G1 that repeats the point it is already at. Each gives a curve with two identical vertices.

NaiveOffset special-cases size() == 1 and skips segments with len == 0. A 2-vertex curve of identical points gets past the first check and then skips its only segment, so cPos and cNeg stay empty. IsClosed() is true, so cPos.m_vertices.front() runs on an empty list (AreaClipper.cpp:559). gdb stops in NaiveOffset without a line number; 559 is the first front() that can reach an empty list.

From reading the code: without assertions, front() and back() on the empty list return the same memory. addJoin sees the points as equal and returns, the writes copy that memory onto itself, and the two empty curves drop out. So Thicken returns nothing for that move.

Who it affects

Any Adaptive op with Rest Machining on, built with this flag and a libstdc++ that has the check, should abort in normal use, not only in the test. Both models tested here had these moves in their roughing paths (46 and 178). This real-use crash was not run outside the test. As far as I know, Fedora and Arch turn this flag on in their default package flags, so distro packages may be exposed. That was not tested either.

The fix

The single-point block in NaiveOffset moves below the segment loop, and its condition changes from curve.m_vertices.size() == 1 to cPos.m_vertices.empty(). One vertex still lands there, because the loop doesn't run. Curves with only zero-length segments now land there too.

The patch is naiveoffset-zero-length.patch. test_thicken_zero_length in TestAreaOperations.py fails on a normal build of main (0 != 1 curves), so CI will catch this from now on. It passes with the patch. clang-format 23.1.0 and black are clean. The file was compiled with the normal -Werror flags.

The patch applies to main 5ce3b8804dd and to releases/FreeCAD-26-3 at b916af74f73. The 26.3 branch has the same NaiveOffset code and the same test (#34111). It was not built or run there.

PaddleStroke's fork commit AstoCAD/FreeCAD@60bce76d59 makes the same fix with the same cPos.m_vertices.empty() check. It shares the circle code through a lambda and adds a Path-level test in TestPathCore.py. The results here were measured on the patch above, not on that commit.

What changes with the patch

A curve of only zero-length segments now behaves like a single vertex in all three NaiveOffset callers.
