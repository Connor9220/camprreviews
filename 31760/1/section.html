TL;DR

  • OK in the Holding Tag panel no longer updates the toolpath. Change a tag's width, move or remove a tag, press OK: the dressup keeps the old path and stays marked for recompute. This hits everyone, with the new option off too. On main, OK rebuilds the path.
  • With Automatically Generate on, hand edits to tags are silently thrown away. A tag removed or moved in the panel comes back on the next recompute, and the panel gives no hint that its edits won't stick.
  • The feature itself works: with it on, tags follow a changed profile, where on main (and with it off) the tags end up disabled and the part is cut free.
  • Migrations are clean both ways: before-feature files open unchanged, PR files open in old FreeCAD unchanged, and the round trip keeps the setting.

What the PR does

It adds a AutomaticallyGenerate property (group "Tag", default off) to the Holding Tag dressup. When it is on, execute() calls generateTags() on every recompute, so the tag positions are rebuilt from the current base path. To keep the task panel's own previews from regenerating, the panel's Apply / Generate / Copy now call execute(obj, False), and the recompute() calls in the panel's accept() and cleanup() are removed. doExecute() is folded into execute(). Old files get the property added (off) in onDocumentRestored().

Feature check (the PR's claim)

Two Tag dressups on the same outer profile, one with Automatically Generate on, one off. Then the profile's Offset Extra goes from 0 to 5 mm:

positions disabled path commands
auto off (= main behavior), before 4 none 28
auto off, after +5 mm 4 (old ring) 0, 1, 2, 3 16 (no tags)
auto on, after +5 mm 4 (moved 5 mm out) none 28

With max count raised to 6, auto-on regenerated 6 tags, and after the +5 mm change still 6 tags on the new outline. So the option does what it says, and it fixes a real hazard: without it, a changed profile quietly drops all tags.

Defects

1. OK in the Holding Tag panel no longer updates the toolpath

The PR removed both FreeCAD.ActiveDocument.recompute() calls from PathDressupTagTaskPanel.accept() / cleanup() (src/Mod/CAM/Path/Dressup/Gui/Tags.py around lines 101-112). accept() still calls getFields(), which writes Width/Height/Angle/Radius/Positions/Disabled onto the dressup, but nothing rebuilds the path afterwards. The dressup is left Touched with the old path. Simulator, post and anything reading Path see the old tags until the user recomputes by hand. This happens with Automatically Generate off, i.e. for every existing user.

Repro (GUI, class tray):

  1. Select the outer profile's dressup, CAM > Holding Tag, OK (4 tags).
  2. Double-click the Tag dressup, set Width to 20 mm, press OK (no Apply).
  3. The path still shows the narrow tags; the dressup is Touched. Recompute: now the 20 mm tags appear.

Measured: PR after OK: Width = 20 mm, state Touched, path unchanged. Same steps with main's accept()/cleanup(): state Up-to-date, path changed. Cancel after Apply also leaves the dressup Touched on the PR (the path itself is restored correctly by the transaction abort).

Pictures: pr_after_ok_stale.png (after OK) and pr_after_manual_recompute.png (after a manual recompute).

The likely reason for the removal is defect 2: a recompute on OK would regenerate the tags and drop the panel's edits. Keeping the recompute on OK (and deciding what the panel should do when auto-generate is on, see below) avoids breaking the default case.

2. With Automatically Generate on, hand edits are silently lost

With the option on, every recompute calls generateTags(), which overwrites Positions and sets Disabled = [] (src/Mod/CAM/Path/Dressup/Tags.py:1228). The panel still offers Add / Remove / Edit / Generate / Copy, and Apply previews the edit (it runs execute(obj, False)), so the user sees their edit take effect. The next recompute of anything upstream throws it away.

Repro:

  1. Set the Tag dressup's Automatically Generate to true, recompute (4 tags).
  2. Open the panel, select tag 0, Remove, Apply: 3 tags, path shows 3.
  3. OK, then change anything upstream (e.g. the profile's Offset Extra) or press Recompute: 4 tags again.

That's a natural consequence of the option, but the panel has no checkbox for it and no hint that edits won't stick. Suggestion: show the option in the panel and disable the manual tag editing while it is on (or turn the option off when the user edits tags by hand). Steps 4-5 of demo.mp4.

From the code (not reproduced)

  • generateTags() falls back to self.execute(obj) (now with regen=True) when pathData is missing, and execute() calls generateTags() again when the option is on, a possible endless recursion (src/Mod/CAM/Path/Dressup/Tags.py:1035). Not reachable today: execute() sets pathData before it calls generateTags(), and setup() failing makes supportsTagGeneration() raise first. Passing regen=False there would make it safe.

Other code-review notes were checked and dropped: the empty-base-wires branch can't happen (findBottomWires() always returns a list); OK committing the transaction before getFields() is the same on main.

Migrations (requested)

"Old FreeCAD" here is this same build with main's versions of the two Tags files (the PR changes only these two Python files), run headless through cam-ab. Each open did a forced recompute (touch() on every op) and compared the dressup's G-code with what was stored.

Scenario Result
Before-feature file (main, 4 tags) opened on the PR Property added, value off; 4 tags, Disabled empty; path identical to stored after recompute. No errors.
PR file (auto on, max count 6, 6 tags) opened on main Loads with no errors; main keeps AutomaticallyGenerate = true as an unused property; 6 tags, path identical after recompute (main doesn't regenerate).
PR → main (saved) → PR AutomaticallyGenerate is still true, min/max count still 4/6, 6 tags, path identical. After a +5 mm profile change the 6 tags regenerate on the new outline.
main → PR (saved) → main Loads fine; the extra property is kept, value off; path identical.

Nothing changes or disappears silently in any direction. One limit: these saves were made headless (no GUI view-provider data), so the GUI side of the round trip was not part of it.

Not in the PR description

  • Task panel OK and Cancel no longer recompute the document (tested: defect 1).
  • Panel Apply / Generate / Copy now run the dressup without regeneration, so their preview can differ from the next recompute when the option is on (tested: defect 2).
  • With the option on, Positions and Disabled are rewritten on every recompute, so removed, moved, added or disabled tags are reset (tested: defect 2).
  • The new option exists only in the Property View; the task panel has no control for it (tested).
  • Auto-generation uses the min/max tag counts stored in the dressup from the panel's spin boxes; these are saved in the file and survive the round trip (tested).
  • ObjectTagDressup.doExecute() is removed and execute() takes a new regen argument; no caller in the tree uses doExecute, outside scripts would break (not tested).

Also on main (not this PR)

  • Unchecking a tag in the panel (Disabled) does not stick: createTagsPositionDisabled() sets tag.enabled = self.pathData.checkTag(tag), overwriting the user's disabled flag, so the next recompute re-enables it. Same on the PR's base commit.
