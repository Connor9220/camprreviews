TL;DR

  • Flexy Height does nothing on circular hole operations. On Drilling, Helix, Tapping and Thread Milling the checkbox is enabled, but the toolpath does not change. Canned cycle links still climb to clearance height.
  • On Pocket and Profile the hop can cut uncut stock. Its height comes from the model only, so the link can become a feed move below the stock top. Main stays above the stock.
  • Links can get slower with it on. A hop below Retract height runs at the vertical feed instead of as a rapid. In one test, link feed time went from 18 s to 47 s.
  • Picking a work plane from a face now gives it a garbled name. An unrelated edit in this PR broke the label, so every such plane is called f{picked.Label.{sub}.

With Flexy Height off, nothing changes: all four prepared files give the same toolpaths as main, and old files load fine.

Canned cycles and circular holes

This is what the requester asked about. The test part was a 140 x 80 x 10 plate with four holes, a low rib (top Z16) and a tall boss (top Z35) between them, Retract Z13 and Clearance Z60.

"Forced through" means a temporary patch in the test session that made Drilling and Helix pass the setting on. Nothing in the tree changed. It shows what the one missing argument would do. On Drilling the cycles stayed intact: the G81/G83 words and R values were unchanged, the moves still ended at Retract height, and G98 and G99 both gave sensible moves. So wiring it in looks low risk for Drilling.

Not tested: posted G-code. Reviews do not post, so how the post closes a cycle group (G80) around a hop was not checked.

Also on main, not this PR: Tapping ignores the collision strategy completely. With Line of Sight, it rapids from X40 Y60 to X100 Y20 at Z13, straight through the Z35 boss. The A/B against main is identical. Flexy Height does not help here, because Tapping has no linking to hook into. Thread Milling also has no linking and always retracts to clearance height.

Defects

1. Flexy Height is ignored on most operations that show it

The checkbox and property appear on every operation with linking, but only get_linking_args() forwards the setting. I recorded each call to the linking code while recomputing the 5-axis test block with Flexy Height on:

Operation Linking calls Calls with Flexy on
Pocket 3 3
Profile (two ops) 3 3
Drilling 1 0
Helix 1 0
MillFacing (two ops) 4 0
Engrave 10 0

Deburr, Flute and the Boundary2 dressup build their own arguments the same way, but that is from reading the code only.

Repro:

  1. Open a Drilling op with a boss between holes and Retract below the boss top.
  2. Set the strategy to Line of Sight and tick Flexy Height.
  3. Recompute. The G-code is the same as with it off.

2. The hop can cut uncut stock

get_extra_clearance_height() only looks at the model. The stock can sit above it, and the template stock here does, by 3.175 mm. The dressup path has a floor for exactly this case (get_dressup_linking_moves), but the operation path does not.

Part: 120 x 60 x 20 block, two pockets with a 20 mm rib between them, stock top Z23.175, default heights, Collision Clearance 1 mm, 6 mm tool.

Link between pockets
Flexy Height off (same as main) G0 at Z26.175, above the stock
Flexy Height on G1 at Z21, 300 mm/min, about 2.2 mm into the stock over the 20 mm rib

Line of Sight and Tool Diameter gave the same result. With the default clearance (the tool diameter, 6 mm) the hop lands at Z26, above this stock, so this needs a clearance smaller than the stock allowance.

Repro:

  1. Pocket two features separated by a rib, with stock above the model.
  2. Set Line of Sight, Collision Clearance 1 mm, Flexy Height on.
  3. Recompute. The link is a feed move below the stock top.

3. Links can get slower with Flexy Height on

Area operations turn every link move below Retract height into G1 at the vertical feed (Area.py:375). With default heights, Retract sits above the stock, so the hop usually lands below it. A long link that was a rapid becomes a slow feed move.

Case (Line of Sight, 300 mm/min vertical feed) Link feed time off Link feed time on
Profile on circular holes, Retract Z41.2, clearance 2 mm 18.3 s 46.6 s
Pocket, default heights, clearance 6 mm 142.5 s 159.1 s

Rapid distance does drop (348 mm to 159 mm on the Profile), but a rapid is far faster than 300 mm/min. The existing rule is on main. This PR is what puts long links below Retract height.

Repro:

  1. Use Profile on holes with a boss between them, default heights, Line of Sight.
  2. Tick Flexy Height and recompute.
  3. The link over the boss changes from G0 to G1 at the vertical feed.

4. Set Work Plane from Face gives a garbled name

Path/Op/Gui/Base.py:359: an unrelated string rewrite produced label="f{picked.Label.{sub}", with the f inside the quotes and a brace missing. On main the label is the object and face, such as Model-Body.Face19. With the PR, every plane made this way gets the same literal text, in the tree and in the Heights page selector, so planes cannot be told apart.

I ran the menu action's handler and selected a face on the class tray. The menu entry itself was not clicked.

Repro:

  1. Right-click an operation and choose Set Work Plane from Face.
  2. Pick a planar face.
  3. Open the operation's Heights page. The work plane is named f{picked.Label.{sub}.

5. The checkbox goes out of sync and overwrites the property

FlexyHeight is not in the pageUpdateData() list, so the checkbox does not follow the property while the panel is open. The next edit to any field writes the old checkbox value back.

Repro:

  1. Open a Profile panel with Line of Sight and tick Flexy Height.
  2. With the panel still open, set Flexy Height to false in the Property View. The checkbox stays ticked.
  3. Change Retract on the Heights page. Flexy Height is true again.

6. Tool Diameter hops are too low beside an obstacle

The hop height is measured from the tool centerline, even under Tool Diameter and Tool Shape. If a tall feature is within the tool radius of the link, the hop fails the check and the link falls back to the old heights, so Flexy Height silently does nothing. It stays safe.

I reproduced this by calling the generator directly, not through an operation: a link 3 mm beside a Z30 rib, 10 mm tool, clearance 1 mm. It tries Z28, which collides, then goes to Z60. A hop at Z31 would have cleared it.

Repro:

  1. Call get_linking_moves() with tool_diameter=10, the link 3 mm beside a Z30 rib, and flexy_clearance_height=True.
  2. The traverse goes to clearance height instead of about Z31.

From the code (not reproduced)

  • Path/Op/Gui/Base.py:1304: compares the property to the checkbox widget, not .isChecked(), so the check is always true. No visible effect found: opening the panel already marks the op as touched without running this code.
  • Path/Op/Gui/Base.py:1354: checkStateChanged needs Qt 6.7 and has no guard, unlike Drilling.py and others, so the Heights page could fail on older Qt. This build uses Qt 6.11, so it could not be tested. Profile.py and Engrave.py already have the same unguarded use.
  • Path/Op/Gui/Base.py:1325: setChecked() runs without blocking signals, unlike the combo above it, so a refresh could re-enter getFields(). I could not trigger a wrong result.
  • Path/Op/Base.py:1819: FlexyHeight is not in SetupPropertiesLinking(). The SetupSheet has the other linking settings but not this one (confirmed on the test files), so a job template cannot set a default.
