PR #33109 - CAM: fix unintended diagonal moves in ramp method 4 (jffmichi)

TL;DR

  • Fix confirmed: Ramp Entry method 4 no longer leaves the final loop with a diagonal move (author's file: one diagonal G0 rising 30 mm over 17.4 mm on main, none on the PR; my plate with outline + 2 holes: 2 diagonal G0s on main, 0 on the PR; with a Profile finishing (spring) pass: 3 diagonal upward feed G1s + 2 diagonal G0s on main, 0 on the PR).
  • Ramp methods 1, 2, 3 and Helix produce byte-identical paths on main and PR (all test files); Profile's own ramp options are identical too.
  • No defects found. Full CAM suite passes (1990 tests, OK).

What the PR changes (Path/Base/Generator/ramp_entry.py, createRampMethod4 only)

  1. The search for the end of the loop now runs backwards from the end of the path (finds the LAST edge that returns to the loop start), so a Profile finishing/spring pass over the same contour gets the extension after it instead of in the middle.
  2. The final-loop extension is only added when the move after the loop is a rapid that goes up (G0 with Z above the loop); otherwise it logs "Expected a retract move after the loop, will not extend the loop" and leaves the path as is. The guard also avoids the IndexError tarman3 hit when the loop is the last move.
  3. X/Y are removed from that retract so it goes straight up; the next horizontal move gets full X/Y.
